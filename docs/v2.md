# V2 Ideas (Conditional)

**Wheely Arrival Companion** — independent concept study by Ayo Ahmed.

Every item below is **conditional on v1 evidence**. None is committed; each exists to capture where the concept could grow if — and only if — testing supports it.

## If the timeline proves useful

- **Contextual stage hints:** airport-agnostic "what to expect next" notes per stage (e.g., what typically follows baggage reclaim).
- **Richer feedback:** let "unclear" say *what* was unclear, via preset options only — still no free text collection.

## If consented updates prove useful

- **Native share sheet:** let the passenger choose any real recipient through the OS — still explicit per send, still preview-first, still generic text. No recipient database, ever.
- **A second message preset** if testers find one generic line insufficient — same consent and preview gates.
- **Optional rough ETA in the update**, only if data shows "too thin" is the top "unclear" reason — currently excluded by design.

## If degraded states matter in testing

- **Independent source recovery:** real browser offline detection exists in v1, but there are no data-source connections. A production proposal would separately model flight and chauffeur freshness, reconnect validation and last-known timestamps rather than assume that reconnect means fresh data.
- **Persistent committed state** (e.g., local storage) so a reload doesn't lose a committed timeline — opt-in, documented, still no server.

## Deliberately not in v2

- Any automatic or background sharing.
- Accounts or analytics; no persistent identity. Optional local continuation would deliberately change v1's reset-on-reload boundary and need validated loading, expiry and deletion controls before adoption.
- Live flight or location data — real integrations change the privacy model and would need a fresh privacy review first.
- Anything that modifies a booking (per the official FAQ, guests can't — and this concept never would).
